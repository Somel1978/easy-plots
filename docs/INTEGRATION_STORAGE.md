# Native adaptive partitions and persisted index tiers (ADR-062/063)

The existing `NativePackRepository` remains the protected storage facade. Every native read still uses an exact `_id` server fetch; no `getIndex()`, unrestricted `getDocuments()` or campaign enumeration was added. Existing GM attestation, native permissions and `DesignatedGMWriter` remain required. Read-back and local serialization are not server CAS or distributed locks.

## Native repository contracts

- `read(id,{partitionId,gm})`, `put(record,{expectedRevision,gm})`, `indexStatus`, `hasReadyIndex`, `query` keep their signatures and stable logical locators. `indexStatus` returns **null** for absence, `prepared` for interrupted first creation (including legacy `pending`), or `ready`.
- Every payload keeps its existing `ep:record:<logicalPartition>:<id>` native key. Narrative IDs, graph references and domain history locators never move. Native index pages split after 8 pages of 32 entries. A hash trie has a maximum depth of 20. Each leaf remains independently bounded at 256 entries.
- `inspectPartition({partitionId,path='',gm})` reads one exact protected manifest and returns `{partitionId,path,tier:'top-level',state,children,migration,policy}`. State is `legacy` for an unsplit root, `leaf` for a split child, `copying` during migration, or `ready` for a branch. `children` lists the two child paths of ready branches. `migration` is `{nextPage,totalPages:8}` only while copying.
- `reconcilePartition({partitionId,path='',maxPages=1,gm})` verifies/copies 1..8 source index pages and returns the inspection plus `{migratedPages,complete}`. It checks persisted source revisions and digests. Restart after the last copied page can publish child manifests without redoing a nonexistent ninth page. Normal overflow performs bounded automatic split repair under the designated writer. Explicit repair can proceed one source page per call.
- `reconcilePage({partitionId,page=0,path='',gm})` repairs prepared entries in one leaf only. After a split, pass the leaf path exposed by `queryIndex`; the source migration must finish before repair changes its digested entries.
- `queryIndex({partitionId,cursor='0:0',limit=16,tier='all',gm})` returns `{items,unresolved,nextCursor}` with at most 32 metadata candidates and **no payload hydration**. An item contains `{id,status,partitionId,path,tier,kind?}`. Tier is `shard` or `historical`; old index entries without tier metadata are explicit `unknown` candidates and must be checked by exact read before exclusion. `tier` accepts `all`, `shard` or `historical`.
- `query` retains the same result shape, with exact payloads instead of metadata. Its storage work is one bounded index page, a bounded manifest path and at most `limit` payload reads. Follow `nextCursor` even when `items` is empty. Unsplit partitions still emit up to 8 pages including empty pages. Split partitions use opaque `t:...` cursors; **never parse cursors or treat a fixed page count as completeness while a cursor remains**. A legacy continuation after a split or a continuation of a newly split leaf raises `CURSOR_STALE`; restart that bounded logical query. Modern cursors are bound to the logical partition.

Copying branches expose their complete unchanged source index until publication. Payloads are not copied. Child indices are published only after all 8 source pages are verified. Missing known child manifests/index pages, truncated known entries, misplaced hash entries and changed source digests fail closed. Ready records with missing payloads remain unresolved; prepared index records never count as absence. Old root index pages remain retained; no destructive cleanup or global migration is performed.

## Tier loading policy

`partition-policy.mjs` classifies every record kind: current and unknown future kinds use `shard`; immutable domain revisions, published graph snapshots/manifests/pages, blueprint revisions and arc archive records use `historical`. `top-level` is the compact native split manifest. The tiers share the same GM-only pack and do not imply public access. Top-level inspection never hydrates shard payloads; index metadata discovery never hydrates history; callers fetch only chosen exact records. Existing unknown legacy metadata remains visible rather than making a negative historical proof.

## Posting buckets (chronology, critical intake, due time)

`BoundedPostingPages` is integrated into `NativeChronologyIndex`, `NativeCriticalSignalIndex` and `NativeTemporalIndex`. Their old single-record bucket locators remain unchanged. The existing capacity option now bounds a **page**, not all durable postings in a bucket. A root stays in the legacy shape until overflow; then an ordered protected directory references immutable, fingerprinted pages. Updating one posting rewrites at most one page (two when splitting), followed by a prepared root and its ready publication. Readers reject prepared roots with `INDEX_UNCERTAIN`; the old view remains retained for exact repair and is never mistaken for complete new coverage. Known missing or modified pages fail closed.

Directories are capped at 128 shards and 60,000 root bytes; individual native records remain capped at 65,536 bytes. These are storage/work limits with explicit `POSTING_BUDGET` exhaustion, not an unlimited-storage claim. Immutable superseded/orphan pages remain unreachable and retained; automatic garbage collection is outside this migration.

- Critical `page({limit=16,cursor=null})` returns its existing items/nextCursor/scannedBuckets plus `scannedPages`, and reads at most 8 posting pages. Its cursor adds optional `version:2`, `page` and `unopened`; old unsplit cursor objects remain accepted. `get` reads only one root and at most one chosen posting page. `reconcile(bucket)` repairs that exact root's prepared migration. Per-bucket local write serialization is preserved.
- Chronology `page(query,{from,to,limit=16,cursor=null})` retains global timestamp/causal-depth/ID order across posting splits. It reads at most 24 posting pages while preserving the existing time-bucket window bound and 32-item bound. Cursors add optional version/page fields and retain query hash and root revision checks. Old cursors reject revisions changed by migration. `reconcile(query,bucket)` repairs one known root. Chronology entries are canonical immutable occurrences; a changed timestamp or depth is a distinct canonical occurrence, not a retargeting of an existing occurrence.
- Temporal `page({from,to,resolveCurrent,maxDue=64,sourceScope='world',cursor=null})` is new. It returns `{from,to,candidates,nextCursor,scannedBuckets,scannedPages,staleCandidates,outcomesInvented:0,effectsExecuted:0,gmReviewRequired:true}`. It reads at most 24 posting pages and keeps the existing finite bucket window and canonical-resolution work budget. Cursor is an opaque object bound to scope, sourceScope, interval and bucket width plus the current bucket revision. Each page revalidates the canonical schedules; candidate pages are sorted individually by due time. Complete `.due(options)` keeps its existing contract and raises `DUE_BUDGET` when a continuation remains. `reconcile(bucket,sourceScope='world')` repairs one known bucket.

For a public GM coordinator wrapper around temporal paging, pass the same resolver as `GMTemporalCoordinator.due`: read `scheduled-commitment` in the selected canonical scope, require matching kind, and return `{sourceRevision:row.revision,dueAt:row.data.dueAt,status:row.data.status}`. Forward `cursor` and retain its opacity. The verified native runtime already exposes `temporalIndex`; it can expose a GM API wrapper without changing this storage contract. Dense catch-up now persists the posting cursor and ordinal inside its current bucket, retaining each immutable page before moving progress. The old first-page locator remains unchanged. `readPage({scope,id,bucket,page:0})` can inspect any retained ordinal. Canonical work exhaustion returns a continuation without raising the per-call work limit; complete `.due` still raises DUE_BUDGET. The 137-schedule interruption/restart test proves complete enumeration without execution.

## Local evidence and limits

New native mocks use only exact `_id` queries, native create/update/read-back, permission checks and designated writers. They cover repeated native overflow, stable locators, empty-page traversal, fresh repository reconstruction, split interruption and final-page ACK loss, prepared entries, corruption, top-level/history lazy metadata, posting overflow and ordered paging, exact posting reconciliation, canonical due validation and cursor staleness. No real Foundry world or multiplayer test was run. Existing attestation requirements remain in effect.

The GM Storage partitions window/API provides exact partition inspection, one-source-page migration reconciliation and metadata-only tier paging. No world scan or history payload hydration is performed. `pageDueCommitments` exposes the coordinator canonical resolver with opaque continuation cursors.
